# Баги PR Reviewer

Ведёт qa. Один баг — один файл. Процесс с 30.10 (решение пользователя Q6–Q9, `agents/backlog.md` → «Маршруты»):
- **Решение «чинить или нет».** Пользователь приносит баг в сессию qa и там же решает, чинить ли его. Без его решения баг не правят: вердикта qa и решения PM недостаточно.
- **Мелочь qa правит сам.** Это текст, формат, однострочная правка. qa коммитит её сам, на английском, `fix: BUG-NNN …`, и пересобирает приложение через `./install.sh --app-only`.
- **Остальное — dev.** qa отдаёт баг dev напрямую и сам проверяет исправление.
- **Вопросы.** Продуктовые («так задумано, но решать надо по продукту») — к PM, визуальные (вёрстка, цвета, тексты) — к designer. PM получает итог одной строкой.
- **Живая проверка.** Рискованные изменения dev сам отдаёт qa на живую проверку.
- **Коммиты.** Файлы `agents/bugs/` коммитит PM.

## Нумерация

`BUG-NNN-короткое-имя.md`: номер — следующий за самым большим в папке, три цифры с ведущими нулями; имя — 2–4 слова латиницей через дефис (`BUG-001-badge-stale-after-resolve.md`). Номера не переиспользуются, даже если баг отклонён.

## Статусы

`новый` → `ждёт решения пользователя` → `подтверждён, правит qa` или `подтверждён, передан dev` → `исправлен (ждёт проверки)` → `закрыт` / `возвращён` (снова к dev с комментарием).

Иначе: `отложен` (баг признан, но пользователь решил не править; остаётся в реестре) / `не баг` (пользователь считает поведение задуманным; если оно ему не нравится — вопрос к PM) / `не воспроизводится`.

Статус меняет qa. История смены — в разделе «История» в конце отчёта.

## Серьёзность

- **S1 — критично**: публикует неверное в Bitbucket, теряет или портит данные (`state.json`, память, бэклог, ветка PR), сервис встал.
- **S2 — серьёзно**: функция не работает или врёт, обходного пути нет.
- **S3 — средне**: работает неправильно и это заметно влияет на работу — обрывает или запускает не ту работу, неделями показывает неверные данные, скрывает поломку.
- **S4 — мелочь**: текст, косметика, неверная цифра без заметного влияния, редкий или пока не проявляющийся случай, сценарий только из терминала.

Цена в отчётах — по тарифам API, а модели работают по подпискам: лишние запуски тратят лимит подписки, а не деньги. Приложением управляют только мышью (поповер в стиле iOS), клавиатура и доступность не учитываются.

## Как воспроизводить безопасно

Сервис живой: launchd будит `run --scheduled` раз в минуту и публикует в Bitbucket. Без явного разрешения пользователя qa не запускает ничего, что публикует комментарии, меняет `config.json`, ветки PR или установленные launchd-агенты и приложение.

**Только чтение — можно:**

- файлы: `~/Library/Application Support/pr-reviewer/` (`state.json`, `status.json`, `*.jsonl`, `prs/`, `queue/`, `arch/`, `qa/`, `memory/`, `backlog.json`), лог `~/Library/Logs/pr-reviewer/worker.log`, `config.json`, клоны в `~/.pr-reviewer/` (только `git log/show/diff`);
- команды: `status`, `stats`, `backlog list|export`, `arch show|list`, `qa show|list`, `memory list|history`, `memory review <slug> --show`, `ignore list`, `help`;
- `launchctl print gui/$(id -u)/com.avoronin.pr-reviewer` — состояние агента.

**Пишут в служебные файлы, но не наружу — можно, если нужно для воспроизведения:** `sync` (только GET к Bitbucket, перезаписывает `prs/`), `limits` (`limits.json`), `agent models cursor` (`cursor-models.json`).

**Изолированная копия данных.** И CLI, и окно берут каталог данных из `HOME`, поэтому баги состояния можно гонять на копии: скопировать `~/Library/Application Support/pr-reviewer` в `<scratch>/home/Library/Application Support/` и запускать `HOME=<scratch>/home bin/pr-reviewer …`. Не изолируются `config.json` (лежит рядом с кодом), Keychain и Bitbucket: команды, которые в них пишут, и так запускать нельзя. Полная изоляция с заглушками — в песочнице ниже.

**Только с разрешения пользователя:**

- `run` без `--dry-run`, `run-now`, `review`, `fix`, `arch`, `qa plan|run|save`, `memory learn|review|apply|restore`, `backlog learn|triage|filed|drop|reopen|close-stale` — публикуют, тратят лимиты моделей или меняют данные;
- `run --dry-run`: в Bitbucket не пишет, но запускает модели (тратит лимиты), берёт `worker.pid` (фоновый проход в это время пропускается), делает `git fetch` в клонах и может переписать `config.json` (`pruneMissingSources` убирает отсутствующие `source`);
- `repo list|add|…`, `pause|resume`, `interval`, `branches`, `agent set`, `token`, `ignore add|remove` — меняют `config.json` или паузу сервиса (`repo list` тоже может переписать конфиг через `pruneMissingSources`);
- `stop`, `fix stop`, `arch stop`, `qa stop` — прерывают чужую работу;
- `install.sh` (полная), `uninstall.sh`, `launchctl bootout|bootstrap|kickstart`.

**Можно без разрешения, после выпуска фичи 1:** `./install.sh --app-only` — пересобирает и перезапускает только приложение, воркер не трогает. О каждом запуске qa пишет в отчёте.

**Проверка исправления в окне.** Установленное приложение само не обновляется. Перед перепроверкой сверить дату сборки с датой правки и при необходимости пересобрать: `./install.sh --app-only`. Новые маршруты API появятся в установленном сервисе только после полной `./install.sh`, на неё нужно разрешение пользователя.

**Окно проверяет сам qa — на копии в песочнице** (решение пользователя через PM, 2026-10-30). Пользователя не ждём. Копию поднимает скрипт `agents/bugs/sandbox/sandbox.sh`:

- код коммита выгружается через `git archive`, рабочая копия не меняется;
- данные — копия папки сервиса, без `api-token` и `worker.pid`;
- сервис — `api serve` на порту 18765 со своим токеном;
- конфиг — копия `config.json` (если его нет — `config.example.json`) со своим портом и CORS для окна;
- окно — vite-сборка приложения на http://localhost:1421/, её открывают во встроенном браузере.

Всё это лежит в `$TMPDIR/pr-reviewer-qa`, в репозиторий и общие папки копия данных не попадает. Установленные приложение и сервис, launchd-агенты, живой `config.json`, Keychain и Docker не трогаются.

- **Команды.**
  - `agents/bugs/sandbox/sandbox.sh up [коммит]` — поднять копию, по умолчанию из `HEAD`;
  - `… down` — остановить;
  - `… data` — заново скопировать данные с живой машины.
  - Порты и папку можно поменять через `QA_API_PORT`, `QA_WINDOW_PORT`, `QA_SANDBOX`.
- **Заглушки Tauri** (`sandbox/qa-shim/`, подключает `vite.qa.config.ts`) записывают в `window.__qa` всё, что окно просит у Tauri и у API:
  - `invokes`, `menu`, `tooltip`, `notifications`, `opened`, `asks`, `requests`;
  - в `popup` — пункты контекстного меню, их выполняет `.action()`;
  - на `ask` заглушка отвечает значением `askAnswer`;
  - `__qa.failPath = /…/` — ответ 409 на подходящие запросы, так проверяется поведение при ошибке;
  - `POST /sync` перехватывается (`blockSync`), иначе окно при открытии запускало бы синхронизацию с Bitbucket;
  - токен API заглушка берёт из `qa-shim/token.js`, который скрипт пишет при запуске. В git токена нет.
- **Заглушки команд** (`sandbox/stub/`) стоят в `PATH` сервиса песочницы и пишут вызовы в `stub.log`:
  - `claude` отвечает содержимым `claude-reply.json` из папки песочницы; файл `claude-fail` вызывает ошибку, `claude-delay` задаёт задержку в секундах;
  - `codex`, `cursor-agent`, `launchctl`, `caffeinate` ничего не делают;
  - `git` — настоящий, но `push` запрещён;
  - `docker image ls` отдаёт список из `docker-images.txt`, `rm` только пишет в журнал, файл `docker-down` изображает упавший демон;
  - `security` — свой Keychain в папке `keychain/`: файл на запись, первая строка — аккаунт, вторая — значение. Поэтому лист токенов в копии проверять можно.
  - Без `QA_SANDBOX` заглушки не работают. Перед стартом скрипт проверяет, что каждая команда берётся из заглушек: пропавшая заглушка молча уступила бы настоящему CLI.
- **Чего копия не покажет:** трей и его меню, нативные уведомления, окно просмотра тестирования, вид на Windows. Их проверяют в установленном приложении — только смотреть, ничего не запускать и не сохранять.
- **Bitbucket.** Действия окна, которые идут к Bitbucket, в копии не работают: токен Bitbucket лежит в настоящем Keychain, а копия его не читает.
- Мелкие правки, как и раньше, сверяем по коду.
