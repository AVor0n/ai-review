# B-35. Open source: публичный репозиторий-витрина для резюме

Автор — PM, 26.11. Решения пользователя: Q29–Q42 (26.11). Связанные строки: B-36 (локализация), B-37 (GitHub PR), B-40 (универсальные настройки).

## Цель

Открыть PR Reviewer как витрину для резюме. По репозиторию должно быть видно три вещи: код, архитектуру и то, как продукт строила команда агентов PM/dev/designer/qa под руководством автора. Чужие установки не цель: issues и устойчивые версии не обещаем (Q29). Если позже захотим, можно дорасти до настоящего open source.

## Решения

- **Q29, витрина.** Репозиторий для чтения. В README честно написано, что продукт — личный инструмент автора.
- **Q30, история.** Открываем сам `AVor0n/pr-reviewer`, предварительно переписав его историю через `git filter-repo`. Отдельный публичный репозиторий не заводим.
- **Q31, Q37–Q39, состав `agents/`:**
  - `backlog.md`, `archive/` — публикуем. Имена клиента заменяем, id сессий `local_…` убираем (Q38).
  - `specs/`, `design/specs/`, HTML-макеты, `design/web/` — публикуем с заменой примеров (Q39).
  - PNG-рендеры старых экранов SwiftUI (`design/mockups/**/*.png`) убираем из всей истории (Q39).
  - `bugs/` — публикуем: все отчёты про баги самого PR Reviewer. Выдержки журналов перед выгрузкой вычитываем: в них не должно остаться кода и обсуждений из рабочих репозиториев. Баги клиентского проекта в этот репозиторий не пишем никогда (Q37).
- **Q40, Q42, замены.** Имя клиента публично не показываем. По всей истории и всем файлам заменяем:
  - имена клиентских репозиториев → `frontend`, `backend`, `android`;
  - прочие упоминания клиента → по смыслу, без имени;
  - ключи задач его трекера → `PROJ-1234`;
  - примеры из его предметной области → тема «интернет-магазин».

  Личные данные автора (имя, email, пути с логином) остаются (уточнение пользователя 27.11, Q55).

  `avoronin` в идентификаторах (`com.avoronin.pr-reviewer`) и авторство коммитов остаются: это автор.
- **Q41, следы агентов.** Строки `Co-Authored-By: Claude` в коммитах остаются. Команда агентов — главная тема README: раздел «Как это построено» со ссылками на бэклог, спецификации, макеты и отчёты qa.
- **Q32, когда.** Открываем после этапа 4, когда SwiftUI удалён. Универсальные настройки (B-40) делаются раньше: без них код всё равно привязан к одному проекту.
- **Q35, лицензия.** MIT.
- **Q36, площадка.** Только Bitbucket Cloud, это прямо написано в README. Поддержка GitHub PR — B-37.

## Что сделать

### B-40. Универсальные настройки (dev, до открытия)

Всё, что было зашито под клиентский проект, переезжает в `config.json`. Значения по умолчанию либо общие, либо отсутствуют (решение пользователя 26.11):

| Что | Сейчас | Станет |
|---|---|---|
| Какие ветки брать в ревью (`branchPattern`) | ключ трекера клиента | любой ключ Jira: `[A-Z][A-Z0-9]+-\d+` |
| Номер задачи из ветки: доработка (`src/fix.mjs`) и QA (`src/qa.mjs`) | только ключ клиента | любой ключ Jira, в коммит доработки идёт ключ целиком |
| Репозитории QA (`qa.frontend`, `qa.backend`) | имена репозиториев клиента | без умолчания: пока не заданы, QA выключено, кнопка объясняет, что настроить |
| Имена Docker-проекта и образа QA | с именем клиента | от имени сервиса: `pr-reviewer-qa`, `pr-reviewer-qa-backend` |
| Короткое имя репозитория в интерфейсе | отрезается префикс клиента | необязательная настройка «префикс для показа», по умолчанию пусто |
| Подсказки в интерфейсе и CLI | ключ клиента | `PROJ-1234` |

Требования:
1. **У пользователя ничего не меняется.** При обновлении сервис сам записывает в его `config.json` текущие значения клиентского проекта: шаблон веток, репозитории QA, префикс для показа. Руками живой `config.json` не правим. SwiftUI не трогаем (он доживает до этапа 4): после записи в настройки он показывает то же, что и раньше.
2. Новые поля описаны в `schema/config.schema.json` и есть в настройках приложения Tauri там, где экран настроек их показывает.
3. QA устроено под стек клиентского проекта: Docker-бэкенд, тестовая база, Playwright. Dev перечисляет, что ещё в нём привязано к этому проекту. Если общим это не сделать, README честно называет QA примером интеграции, который требует своей настройки.
4. Тесты на `frontend`, `backend` и `PROJ-…` вместо имён клиента. `npm test` и тесты приложения проходят.
5. После правки в коде и тестах нет имени клиента и ключа его трекера — проверка `git grep` по ним вне `agents/`.
6. В правиле бэклога «Передача» вместо «имя клиента и его ключ хардкодить можно» — «имена проектов только в настройках».

### Открытие (после этапа 4)

1. **Подготовка (PM, designer).**
   - Таблица замен и список файлов на удаление из истории.
   - Вычитка выдержек журналов в `bugs/`.
   - Сверка PNG, которые остаются, если такие есть.
2. **README (dev, PM).**
   - Английский основной, `README.ru.md` — русский (B-36, Q34).
   - Что это и почему только Bitbucket.
   - Архитектура: сервис, API, приложение Tauri.
   - «Как это построено» — команда агентов.
   - Установка для тех, кто захочет попробовать.
   - Лицензия MIT, файл `LICENSE`.
3. **Переписывание истории (dev).**
   - Сначала полная резервная копия: `git clone --mirror` в отдельную папку.
   - Затем `git filter-repo`: замены по таблице, удаление PNG.
   - Проверка: поиск имени клиента по `git log --all -p` пуст, `npm test` проходит на последнем коммите.
   - После этого все рабочие копии и сессии переходят на новую историю: старые клоны пересоздаются.
4. **Открытие (пользователь).** Пользователь смотрит репозиторий и сам переключает его в публичный на GitHub. Это действие делает только он.

## Проверка

- qa после B-40: на копии данных ревью, доработка и QA работают со значениями клиентского проекта из настроек так же, как до правки. На пустых настройках QA выключено с понятной подсказкой.
- PM перед открытием: поиск по всей переписанной истории на имя клиента, ключ его трекера, имена из реальных PR. Выборочная вычитка `bugs/`.
