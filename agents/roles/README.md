# Роли и перезапуск сессий

Над PR Reviewer работают связанные сессии Claude Code по ролям. У каждой роли свой файл: по нему сессию можно очистить в любой момент и продолжить без потерь — этому же человеку или другому, на этой машине или на другой.

| Роль | Файл | Зона |
|---|---|---|
| Продукт-менеджер | [pm.md](pm.md) | продуктовые решения, доска, спецификации, порядок очереди |
| Разработчик | [dev.md](dev.md) | код, тесты, сборка |
| Дизайнер | [design.md](design.md) | UI/UX, макеты, дизайн-система |
| Тестировщик | [qa.md](qa.md) | баги, живая проверка, отчёты |

Одна роль — один файл, даже если сессий у неё несколько. Если у роли две сессии, каждая строка «В работе» начинается с имени сессии, чтобы новая сессия брала только свою.

## Сессии

Файлы ролей общие и лежат в git: по ним разработку продолжит кто угодно, на любом Mac, с тем же контекстом. Id сессий `local_…` — нет: они существуют только на машине, где созданы. Поэтому таблица «роль → id сессии» локальная — `agents/roles/sessions.local.md`, файл в `.gitignore`.

- **Формат** — строка на сессию: `| Роль | local_… |`, у роли с несколькими сессиями — несколько строк.
- **Новая сессия** (или первая на этой машине) после того, как узнала роль, дописывает себе строку. Нет файла — создаёт его с заголовком таблицы `| Роль | Сессия |`. Коммитить не нужно.
- **Писать другой роли** — по id из этого файла (`SendMessage`). Если у роли ещё нет сессии, скажи пользователю: сессию создаёт он, или ты предлагаешь её карточкой.
- **Переезжает только git:** файлы ролей, бэклог, спецификации, макеты, отчёты. Не переезжают память Claude (`~/.claude/projects/…`), scratchpad, установленный сервис и приложение, `config.json`, Keychain. Поэтому правила и состояние держим в файлах ролей, а не в памяти.
- **Работаем на одной машине за раз.** Перед переходом каждая роль обновляет «В работе», коммитит свой файл и пушит `main`. На новой машине — `git pull`, установка (`./install.sh`, разрешает пользователь), свой `config.json`. Незаконченная ветка задачи не переезжает: dev перед переходом доводит её до `main` или спрашивает пользователя, можно ли запушить ветку.
- После `/clear` id сессии не меняется, адресация не ломается.

## Маршруты (решение пользователя, Q6–Q9, 30.10)

Сессии пишут друг другу напрямую. PM получает только то, что требует продуктового решения, и итоги. Сообщение без изменений не пересылаем: лишнее звено (пересылка, двойная проверка, повторный вопрос пользователю) убираем.

- **Очередь dev** — колонка Todo на доске сверху вниз, порядок задаёт PM. Dev сам берёт верхнюю задачу и отчитывается один раз на задачу: комментарием в issue и одной строкой PM. В отчёте — коммит, тесты, что проверено вживую, а что нет. PM коммиты не перепроверяет.
- **Баги.** Пользователь приносит баг в сессию qa и там же решает, чинить ли его. Вердикта qa или решения PM без пользователя недостаточно; задача от PM, где сказано, что пользователь её одобрил, считается одобренной. Каждый баг — issue с меткой `bug`, подробный отчёт — файл в `agents/bugs/`. Мелочь (текст, формат, однострочная правка) qa правит сам, остальное отдаёт dev и сам проверяет исправление.
- **Дизайн.** Designer согласует макет с пользователем, пишет спецификацию и сам ставит задачу dev. PM получает строку с путём и заводит или обновляет issue.
- **Проверка.** Рискованные изменения (состояние, очередь, данные, уведомления) dev отдаёт qa на живую проверку. Экранная проверка руками пользователя — только для сложных задач; мелкие визуальные правки сверяются по коду, на экране их со временем смотрит пользователь.
- **Коммиты.** `agents/` коммитит PM отдельными коммитами `docs:`; свой файл роли каждая роль коммитит сама. Код коммитят dev и qa.

## Решения не живут в чате

Решение пользователя сразу записывается туда, где его будут искать:

- продуктовое — в issue и спецификацию `agents/specs/` (через PM, с номером вопроса: «(Q7, 30.10)»);
- визуальное — в макет `agents/design/mockups/` и отметку об одобрении в issue экрана;
- про баг — в issue бага (qa);
- про установку и настройку — в `README.md`.

В файле роли — только ссылка.

## Файл роли

Не больше 1–2 страниц, три раздела:

1. **Постоянное.** Суть роли, правила, где артефакты, кому что передавать. Меняется редко.
2. **В работе.** До 10 строк. Каждая — ссылка на артефакт и следующий шаг, а не пересказ: «#66: жду одобрения макета → спецификация → Todo».
3. **Уроки.** Неочевидное, на что уже наступали: ограничения песочницы, ловушки сборки.

Общие правила — один раз в `CLAUDE.md`. В файле роли — только особое для роли.

## Когда чистить

- Задача закрыта: отчёт отправлен, ответа ни от кого не ждёшь.
- Контекст заполнен больше чем на 50 %, даже посреди задачи.

Перед чисткой сессия обновляет «В работе» и «Уроки» в своём файле, коммитит и пушит его (`docs: roles <роль> …`). После `/clear` достаточно написать «продолжай»: блок «Кто я» в `CLAUDE.md` велит сессии найти свой id в `sessions.local.md` и прочесть файл роли.

`clear_session` не чистит сессию, открытую у пользователя на экране или с включённым Remote Control. Тогда пользователь сам делает `/clear` и пишет «продолжай».
