# Бэклог PR Reviewer

Ведёт PM. Новая идея сразу добавляется строкой в таблицу. Прорабатываем её, только если пользователь попросит. Подробности сделанного до 30.10 лежат в `product/archive/backlog-2026-10-30.md`.

- **Статусы:** идея → проработка → готово к работе → в работе → сделано / отклонено.
- **Размер:** S — без продуктовых вопросов, сразу в работу; M — короткий раунд вопросов; L — отдельная спецификация.
- **Вопросы к пользователю** нумеруются сквозной нумерацией на весь проект. Решения в спецификациях помечаются вопросом и датой: «(Q7, 30.10)».

## Маршруты (решение пользователя, Q6–Q9, 30.10)

Сессии пишут друг другу напрямую. PM получает только то, что требует продуктового решения, и итоги.

- **Очередь dev** — это строки таблицы со статусом «готово к работе». Порядок задаёт PM. Dev сам берёт следующую задачу и отчитывается PM один раз на задачу: коммит, `npm test`, что проверено вживую, а что нет. PM коммиты не перепроверяет.
- **Баги.** Пользователь приносит баг в сессию qa и там же решает, чинить ли его. Мелочь (текст, формат, однострочная правка) qa правит сам. Остальное qa отдаёт dev напрямую и сам проверяет исправление. Продуктовые вопросы идут к PM, PM получает итог одной строкой.
- **Дизайн.** Designer согласует макет с пользователем, пишет спецификацию и сам ставит задачу dev. PM получает одну строку с путём, а строку в таблице ведёт PM.
- **Проверка.** Рискованные изменения (состояние, очередь, данные, уведомления) dev сам отдаёт qa на живую проверку. Остальное пользователь проверяет, пользуясь приложением.
- **Коммиты.** Файлы `product/` коммитит PM, отдельными коммитами `docs:`. Код коммитят dev и qa. Сообщения коммитов пишутся на английском.

## Правила

- **Визуальное направление** — iOS-стиль, всё приложение живёт в поповере из строки меню. Клавиатура и доступность вне рамок. UX-приёмы macOS — только после обсуждения с пользователем.
- **Экранная проверка** нужна только для сложных задач. Мелкие визуальные правки сверяются по коду, на экране их смотрит пользователь. Для экранной проверки qa держит отдельную копию окна с песочницей данных (`product/bugs/README.md`).
- **Установка.** `./install.sh --app-only` dev и qa запускают без разрешения и пишут о нём в отчёте. Полная `./install.sh` только с разрешения пользователя, она ждёт конца прохода (`--now` — сразу). Перед пересборкой нужно сделать коммит.
- **Передача.** Приложение может перейти компании и работать от имени другого человека или системного аккаунта. `project` и `PROJ-` хардкодить можно. Личные данные (email, пути, репозитории, токены) хранятся только в `config.json` (он в `.gitignore`) и Keychain. Значения по умолчанию задаются в коде и схеме, живой `config.json` руками не правим.
- **Репозиторий** приватный на GitHub: `AVor0n/pr-reviewer`, `origin` (создан 25.11). После каждого влития или коммита в `main` тот, кто это сделал (dev, qa, PM), сразу пушит `main` (решение пользователя 25.11). Ветки задач не пушим.
- **Документация** — только `README.md` (Q10, 30.10): при передаче новому владельцу объяснит сессия Claude по коду. Dev правит README в том же коммите, если меняются установка или настройка. Техподдержка закрыта (Q11, 30.10): вопросы о приложении — к PM или в новую сессию.
- **«Прервать» у PR** отменяет работу только этого PR, идущую или стоящую в очереди. Общий stop прерывает весь проход (BUG-005/017).
