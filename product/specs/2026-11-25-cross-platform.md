# B-27. Переезд на Windows 11: сервис в WSL2 и приложение в трее для Windows и macOS

Автор — PM, 25.11. Решения пользователя: Q23–Q27 (25.11).

## Зачем

Сервис переезжает на ноутбук с Windows 11. Сейчас он привязан к macOS: Keychain, launchd, `caffeinate`, пути `~/Library`, Cursor с подменённым HOME. Окно в строке меню написано на SwiftUI и на Windows не работает. Пользователь хочет одно нативное приложение в трее для обеих систем. Объём кода не ограничение: код пишут агенты.

## Решения

- **Q23 — стек приложения: Tauri 2.** Нативный трей и окно-поповер у значка, системный веб-движок (WebView2 на Windows, WKWebView на macOS), одна кодовая база. iOS-стиль в поповере (правило проекта) повторяется в CSS одинаково на обеих системах.
- **Q24 — связь с сервисом: локальный HTTP API.** Сервис слушает `127.0.0.1`. Приложение получает данные, команды и поток событий только через API, файлы данных напрямую не читает. Доступ — по токену из локального файла с правами только для владельца. WSL2 пробрасывает `localhost` в Windows.
- **Q25 — сервис на Windows работает в WSL2 как Linux.** Нативный порт сервиса под Windows не делаем.
- **Q26 — новое приложение заменяет SwiftUI и на macOS.** Когда возможности сравняются, SwiftUI удаляется.
- **Q27 — этапы:** 1 → 2 → 3 → 4, переезд возможен уже после этапа 1.

## Этап 1 (B-28). Сервис на Linux/WSL2

Цель: сервис работает на macOS как сейчас и на Linux, в том числе в WSL2 с включённым systemd. Окна на Linux нет. Результат ревью виден по статусу «AI-review» в Bitbucket (B-26). Уведомлений из сервиса на этом этапе нет: сейчас их показывает только окно SwiftUI. Отправку в Telegram из сервиса не делаем (Q28, 25.11).

1. **Слой платформы.** Один модуль, который знает про ОС, остальной код зовёт только его:
   - **Секреты.** На macOS — Keychain, как сейчас. На Linux — `secret-tool` (libsecret), если он есть, иначе файл в каталоге конфигурации с правами `600`. Имена сервисов и аккаунтов те же, что в `config.json`. Значения секретов никто не печатает и не пишет в журнал.
   - **Не засыпать во время работы.** На macOS — `caffeinate`. На Linux — `systemd-inhibit`, если есть, иначе ничего. В WSL сон задаёт Windows, это описывается в README.
   - **Пути.** На macOS — как сейчас. На Linux — по XDG: данные в `~/.local/share/pr-reviewer`, журналы в `~/.local/state/pr-reviewer`, служебные клоны остаются в `~/.pr-reviewer`.
   - **Расписание и «запустить сейчас».** На macOS — launchd и `launchctl kickstart`. На Linux — systemd user service и timer раз в минуту, `systemctl --user start`.
   - **Cursor.** Ссылка на `~/Library/Keychains` в подменённом HOME делается только на macOS. На Linux нужно проверить, где `cursor-agent` хранит вход, и повторить то же.
2. **Установка.** `install.sh` определяет ОС. На Linux он ставит unit-файлы systemd и проверяет, что systemd включён: в WSL это `/etc/wsl.conf` → `[boot] systemd=true`. Если нет — понятное сообщение, что сделать. Команда для ввода секретов спрашивает значение сама и сохраняет его, не показывая. `uninstall.sh` убирает unit-файлы.
3. **Перенос данных.** Команда экспорта на Mac собирает в архив данные сервиса: память, статистику, исходы, бэклог, состояние, журналы исследований. Без клонов, рабочих папок и секретов. Команда импорта на новой машине раскладывает архив по путям Linux. Клоны создаются заново при первом проходе. `config.json` переносится в архиве. Если в нём есть пути, специфичные для Mac, импорт их называет.
4. **Проверка.** `npm test` на macOS. Слой платформы проверить в Linux-контейнере (Docker, Ubuntu): пути, секреты файлом, unit-файлы, импорт. Живую проверку на WSL2 делает пользователь на новом ноутбуке по шагам из README, dev готовит эти шаги. qa проверяет на копии, что на macOS ничего не изменилось.
5. **README:** установка на Linux/WSL2, перенос с Mac, известные ограничения (окна на Linux пока нет).

## Этап 2 (B-29). Локальный HTTP API

Всё, что сейчас окно читает из файлов и делает через CLI, доступно через API: снимки PR, статус и ход прохода, лимиты, статистика, память, бэклог, архитектурное ревью, доработка, QA, настройки. Поток событий через SSE. Токен лежит в файле с правами только для владельца. Слушать только `127.0.0.1`. Подробная спецификация — перед началом этапа.

## Этап 3 (B-30). Приложение на Tauri

Дизайнер переносит макеты и правила iOS-стиля в общий веб-стиль. Порядок: поповер (список PR, лимиты, запуск, баннеры) → статистика → память → архитектурное ревью → доработка → QA → настройки. Сборка для macOS и Windows. Подробная спецификация — перед началом этапа.

## Этап 4. Паритет и удаление SwiftUI

Сверка возможностей по списку экранов SwiftUI. Когда пользователь подтвердит паритет, `menubar/` удаляется, `install.sh` ставит приложение Tauri.

## Вне рамок

- Нативный порт сервиса под Windows без WSL.
- Работа сервиса на одной машине, а окна на другой.
