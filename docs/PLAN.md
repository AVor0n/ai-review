# План документации PR Reviewer

Черновик для обсуждения с пользователем и PM. Пока план не согласован, README не переписывается; в нём правятся только фактические ошибки.

## Зачем делить README

README — 190 строк, но 71 КБ: абзацы по 2–4 тысячи знаков, справочник смешан с описанием поведения. Ответ на простой вопрос («почему модель не ревьюит этот PR», «что значит оранжевая иконка») приходится искать по всему файлу. Список команд в README покрывает примерно половину CLI.

## Читатели

1. **Пользователь сервиса** — ставит, настраивает, смотрит окно, разбирает замечания.
2. **Команда проекта** (PM, dev, qa, designer) — нужен точный справочник поведения, файлов и полей, чтобы не читать код ради каждого вопроса.

## Структура

```
README.md            — что это, быстрый старт в 5 шагов, ссылки в docs/
docs/
  README.md          — оглавление: какой файл на какой вопрос отвечает
  overview.md        — архитектура и поток данных одного прохода
  install.md         — требования, токены, установка, обновление, удаление
  config.md          — справочник config.json по полям
  cli.md             — справочник команд CLI
  review.md          — как идёт ревью: раунды, ответы, закрытие тредов, скоуп, пропуски
  window.md          — menubar-приложение: иконка, вкладки, бейджи, уведомления, настройки
  fix.md             — доработка по замечаниям и rebase
  arch.md            — архитектурное ревью
  qa.md              — тестирование в браузере
  backlog.md         — бэклог проблем вне скоупа PR
  memory.md          — память ревьюеров
  stats.md           — статистика, исходы замечаний, цена и лимиты
  data.md            — файлы и каталоги: что где лежит, кто пишет и читает
  troubleshooting.md — FAQ и разбор типичных проблем
```

### Что в каждом файле

- **overview.md** — схема: launchd → `run --scheduled` → Bitbucket API и служебный клон → модели → публикация → `state.json`/`status.json`/`prs/` → окно. Один проход по шагам. Очередь явных заявок, лок `worker.pid`, пульс `heartbeat`. Отдельные фоновые процессы (`fix-worker`, `arch-worker`, `qa-worker`, задачи бэклога) и почему они не блокируют ревью. Словарь: проход, раунд, голова PR, тред, заявка, роль (`first`/`second`/`replies`).
- **install.md** — требования (Node ≥ 22, `claude`, `codex`, `git`, `swiftc`; необязательно `cursor-agent`; Docker для тестирования). Три токена в Keychain (Bitbucket, Claude, Cursor) и их сроки. Что делает `install.sh` (пути зашиваются в `bin/pr-reviewer`, первая установка на паузе). Первая проверка `run --dry-run`. Обновление после правок кода: повторный `install.sh`. Удаление.
- **config.md** — каждое поле: тип, умолчание в коде, где меняется в окне, какой командой. Источник — `schema/config.schema.json` и места в `src/`, где берутся умолчания.
- **cli.md** — все команды из `help`, сгруппированные: сервис, ревью, настройки, репозитории, доработка, архитектура, тестирование, бэклог, память. У каждой: что делает, что меняет (Bitbucket, `config.json`, данные, лимиты моделей), работает ли на паузе. Матрица «безопасно / меняет данные / публикует» — по образцу `product/bugs/README.md`.
- **review.md** — когда PR ревьюится и когда нет (`branchPattern`, черновики, пауза, `auto: false`, пустой дифф, rebase без изменений, исключённые файлы). Чередование моделей. Согласие и несогласие, `agreesWith`, `reason`. Закрытие своих тредов (`fixed`, `dismissed`, `deferred`). Оси `origin` и `likelihood`. Привязка к строкам диффа. `repliesEffort`. Как это выглядит в Bitbucket: примеры текстов замечания, ответа, отметок.
- **window.md** — иконка в строке состояния и её состояния; обзор (иконки моделей, бейджи, кнопки доработки, архитектуры, тестирования); вкладки; настройки; токены; уведомления и «Не беспокоить»; баннеры. Скриншоты — по согласованию с designer.
- **fix.md, arch.md, qa.md, backlog.md, memory.md** — разделы README, разбитые по режимам; в каждом — как запустить из окна и из терминала, что делает модель и что ей разрешено, где результат, сколько стоит, как прервать.
- **stats.md** — вкладка «Статистика» по разделам, файлы `stats.jsonl`, `outcomes.jsonl`, `skips.jsonl`, `spend.jsonl`, `fixes.jsonl`, `arch.jsonl`, `qa.jsonl` с полями. Как считается исход замечания. Цена по тарифам API и лимиты подписок.
- **data.md** — таблица файлов `~/Library/Application Support/pr-reviewer/`, `~/.pr-reviewer/`, логов и launchd: назначение, кто пишет, кто читает, можно ли удалить и что будет.
- **troubleshooting.md** — 401/403 от Bitbucket; нет токена в Keychain; «предыдущий запуск ещё идёт»; зависший проход и баннер «Прервать»; модель не ревьюит PR; Cursor без ключа или без лимитов; правка в `menubar/` не видна (нужен `install.sh`); невалидная память; блокировки git после сна Mac; где смотреть журнал. Пополняется по вопросам пользователя.

## Порядок работы

1. Согласовать структуру с пользователем и PM.
2. Сначала справочники, которые проще всего проверить по коду: `cli.md`, `config.md`, `data.md`.
3. Затем `overview.md`, `review.md`, `install.md`.
4. Разделы по режимам — переносом из README с проверкой по коду.
5. `window.md` — вместе с designer.
6. В конце сократить корневой README до быстрого старта и ссылок.

Каждое утверждение проверяется по коду; в спорных местах в тексте документации ссылки на код не ставятся, но держатся в заметках техподдержки, чтобы обновлять документацию после правок dev.

## Вопросы

- Документация для одного пользователя или её будут читать коллеги? От этого зависит, нужен ли английский и насколько подробна установка.
- Скриншоты окна: нужны ли, и кто их снимает (designer или по запросу у пользователя)?
- Корневой README: сократить до быстрого старта или оставить полным, а `docs/` сделать справочником?
