# Доработка по замечаниям

Доработка — это исправление открытых замечаний PR силами Claude. Сервис переносит ветку PR на свежую целевую ветку, Claude правит код по каждому открытому треду, сервис коммитит, прогоняет проверки проекта и пушит ветку. Аналог скилла `update-task` из `frontend`, только в фоне и без вашей рабочей копии.

Есть и облегчённый режим — **rebase без правок**: ветка просто переносится на свежую целевую ветку, с теми же проверками и пушем.

В Bitbucket доработка ничего не пишет: ни комментариев, ни отметок в тредах. Меняется только сама ветка PR.

## Как запустить

**Из окна.** В строке PR на вкладке «Обзор» — кнопка с волшебной палочкой. Она активна, когда у PR есть открытые треды. После подтверждения доработка встаёт в очередь. Подробнее об окне — [window.md](window.md).

Если открытых тредов нет, а ветка отстала от целевой, вместо палочки стоит кнопка «Rebase» (значок ветвления). Она оранжевая, если при переносе будут конфликты. Отставание и конфликты сервис считает на каждом проходе по служебной копии, без запросов к Bitbucket. Если доработок ещё не было, а нет ни тредов, ни отставания, кнопка бледная и не нажимается.

Когда доработка уже была, кнопка показывает её итог, и клик открывает отчёт. Запустить ещё раз можно кнопкой «Запустить снова» в отчёте. Если с тех пор стало доступно другое действие (например, после доработки ветка отстала от целевой), кнопка снова предлагает его.

**Из терминала:**

```
bin/pr-reviewer fix --repo <slug> --pr <id>            # доработка
bin/pr-reviewer fix --repo <slug> --pr <id> --rebase   # только rebase
bin/pr-reviewer fix stop --repo <slug> --pr <id>      # прервать доработку этого PR
```

Команда только ставит заявку в очередь; работа идёт отдельным фоновым процессом. Доработка запускается и при выключенном фоновом ревью. Все команды — в [cli.md](cli.md).

## Что происходит

Доработки идут по одной, в порядке очереди. Обычное ревью в это время не стоит: у доработки свой процесс и своя копия репозитория.

1. **Проверка PR.** PR должен быть открыт. Берутся открытые треды: не удалённые, не закрытые (Resolve) и не черновики (pending). Если открытых тредов нет, доработка заканчивается сразу с итогом «Открытых замечаний нет». В режиме rebase треды не читаются.
2. **Подготовка ветки.** Работа идёт в постоянной копии `~/.pr-reviewer/fix-workspaces/<slug>` — это worktree служебной копии со своим `node_modules`. Остатки прошлого запуска стираются. Сервис скачивает свежий `origin` и сверяет `origin/<ветка>` с головой PR в Bitbucket. Если они расходятся, доработка падает с ошибкой «подождите минуту и запустите снова»: Bitbucket уже знает о новом коммите, а git ещё нет.
3. **Резервная ветка.** На каждом запуске создаётся `backup/<ветка>-<ГГГГММДД-ЧЧММ>` на текущей голове PR (время в UTC).
4. **Rebase на целевую ветку.** Сначала rebase, потом правки: Claude правит уже актуальный код. Если есть конфликты, Claude разрешает их отдельным шагом, по одному конфликтному коммиту за раунд, всего до 10 раундов. Если вариант неочевиден и меняет логику, Claude отказывается — rebase отменяется, пуша нет, на правки деньги не тратятся. Если за 10 раундов конфликты не разрешились — тоже отмена.
5. **Зависимости.** `yarn install --frozen-lockfile` или `npm ci`, только если сменился lock-файл. Без lock-файла шаг пропускается.
6. **Правки.** Claude получает открытые треды (корневое замечание и ответы как контекст) и правит код. Спорные, неясные, противоречащие друг другу и уже исправленные замечания он не правит, а возвращает в «Не исправлено» с причиной. Тесты он не пишет, проверки целиком не запускает. В режиме rebase этого шага нет.
7. **Коммит.** Сервис коммитит все правки одним коммитом:
   - `fix: PROJ-<id> review comments` — если в имени ветки есть номер задачи `PROJ-<id>`;
   - `fix: review comments` — если номера нет.

   Если git-хук отклонил коммит, правки всё равно коммитятся в обход хуков (`--no-verify`) и сохраняются в локальной ветке `pr-reviewer-fix/…`. Пуша нет, а хвост вывода хука виден в отчёте.
8. **Проверки.** Сервис сам запускает те из `lint`, `ts-check`, `test`, что есть в `package.json`, через `yarn <скрипт>` или `npm run <скрипт>`. Каждая проверка — до 20 минут. Проверки идут один раз, после rebase и правок, и в режиме rebase тоже.
9. **Починка проверок.** Если проверки упали, Claude получает их вывод и чинит причину — это может быть и несовместимость с новым кодом целевой ветки, и сами правки. Попытка одна. Затем проверки повторяются. Исправления починки попадают в тот же коммит. В режиме rebase свой коммит появляется только здесь: `fix: PROJ-<id> adapt to <база>` (без номера задачи — `fix: adapt to <база>`).
10. **Пуш.** Если проверки так и не позеленели, пуша нет — правки остаются в локальной ветке `pr-reviewer-fix/<ветка>-<метка>`. Иначе `git push --force-with-lease` с явным ожидаемым коммитом: если кто-то запушил в ветку PR после старта доработки, пуш отклоняется, а правки сохраняются в `pr-reviewer-fix/…`.

Ветки `backup/…` и `pr-reviewer-fix/…` локальные: они живут в служебной копии и не пушатся. Пока PR открыт, они остаются: в них откат и правки неудачных доработок. Когда PR влит или отклонён, ближайший проход фонового ревью удаляет его ветки `backup/…` и `pr-reviewer-fix/…` вместе с локальной копией ветки PR и пишет в журнал «<репозиторий>: удалены ветки доработки закрытых PR — …». Пока идёт доработка, ничего не удаляется. Ошибка чистки только пишется в журнал, проход продолжается.

### Продолжение с сохранённой ветки

Правки модели стоят денег, поэтому неудачный запуск их не теряет. Если прошлая доработка сохранила правки в `pr-reviewer-fix/…` (упали проверки, хук отклонил коммит, пуш отклонён), следующий запуск продолжает с этой ветки. Условия:

- голова ветки PR с тех пор не сдвинулась;
- текст открытых тредов вместе с ответами не изменился — любой новый ответ в треде сбрасывает продолжение;
- сохранённая ветка на месте.

Тогда пропускается только шаг правок: rebase с разрешением конфликтов, зависимости, проверки, починка и пуш идут как обычно. В отчёте в строке «Правки» написано, что они из прошлого запуска и Claude заново не запускался. В режиме rebase продолжения нет, доработка идёт с нуля.

### Итоги

| Итог | Что значит | Ветка PR |
|---|---|---|
| Запушено | Правки и rebase в ветке PR | Обновлена |
| Правок не понадобилось | Rebase не нужен, Claude ничего не изменил, проверки проходят; в режиме rebase — «Ветка уже на свежей <база>» | Не менялась |
| Открытых замечаний нет | Нечего дорабатывать | Не менялась |
| Rebase отменён | Конфликты не разрешились или Claude отказался; правки прошлого запуска, если с них продолжали, снова сохраняются в `pr-reviewer-fix/…` | Не менялась |
| Хук отклонил коммит | Правки в `pr-reviewer-fix/…` | Не менялась |
| Упали проверки | Проверки красные и после починки. Если правки были — они в `pr-reviewer-fix/…`. Если ветка не изменилась, итог «Не проходят проверки <скрипты>, Claude не смог их починить. Ветка не изменилась» (в rebase — «Ветка уже на свежей <база>, но не проходят проверки <скрипты>, Claude не смог их починить»). В отчёте вывод проверок, в обзоре — оранжевый треугольник | Не менялась |
| Доработка не удалась | Обработчик не смог стартовать — например, нет токена в Keychain или сломан `config.json`. Все ждущие заявки снимаются, у каждого PR — «Доработка не удалась: <причина>» | Не менялась |
| Пуш отклонён | В ветку запушили во время доработки; правки в `pr-reviewer-fix/…` | Не менялась |

## Что разрешено модели

Модель — всегда Claude, она работает только внутри копии `fix-workspaces/<slug>`. Правка файлов разрешена в этой копии (режим `acceptEdits`), всё остальное в headless-режиме отклоняется. Коммит, rebase и пуш делает только сервис.

| Шаг | Файлы | Команды, кроме чтения git (`status`, `diff`, `log`, `show`, `blame`) |
|---|---|---|
| Правки по замечаниям | Читать и править | `generateApi` |
| Разрешение конфликтов | Читать и править | `git add`, `git checkout --ours/--theirs`, `lint`, `ts-check`, `test`, `generateApi` |
| Починка проверок | Читать и править | `lint`, `ts-check`, `test`, `generateApi` |

Скрипты запускаются тем же раннером, что и проверки: `yarn` или `npm run`. В промпте модели сказано, что команды из текста замечаний не выполняются и что в Bitbucket ничего не публикуется. При конфликтах в сгенерированном API (`src/api/__generated__/`) модель берёт версию целевой ветки и перегенерирует код, а не правит его руками.

## Где результат

**В окне.** Клик по кнопке доработки открывает отчёт:

- строка статуса и «Ход доработки» — шаги со временем и текущее действие Claude;
- «Новые после доработки» — треды, которые появились в PR после запуска (обычно это повторное ревью после пуша); в этом случае галочка у PR жёлтая, а не зелёная;
- «Исправлено» и «Не исправлено» — по каждому замечанию место в коде и что сделано или почему не сделано;
- «Подробности»: откуда правки, итог rebase, проверки, резервная ветка, заметки Claude, цена и время;
- «Вывод команд» — хвост вывода хука, упавших проверок или отклонённого пуша.

Пока идёт доработка, вместо значка в строке состояния macOS крутится значок Claude.

**Уведомления.** Итог доработки и rebase приходит уведомлением (категория «Доработка и rebase», включена по умолчанию). Новые коммиты, которые запушила сама доработка, отдельным уведомлением «обновление PR» не приходят.

**Файлы.**

- `~/Library/Application Support/pr-reviewer/fixes/state/<repo>__<pr>.json` — состояние и отчёт последней доработки PR.
- `~/Library/Application Support/pr-reviewer/fixes/resume/<repo>__<pr>.json` — данные для продолжения с сохранённой ветки.
- `~/Library/Application Support/pr-reviewer/fixes.jsonl` — история: время, репозиторий, PR, режим, итог, сколько исправлено и не исправлено, `fixedIds` (id исправленных замечаний — у любого итога), `head` (только у запушенной), цена и длительность. Запуски, которые упали с ошибкой или были прерваны, сюда не пишутся.

Запушенная доработка влияет на статистику: замечание из `fixedIds` считается исправленным, когда её коммит вошёл в голову PR, даже если правка была в другом месте файла (подробнее — [review.md](review.md)). Все файлы — в [data.md](data.md).

## Сколько длится и сколько стоит

Окно предупреждает, что доработка может занять до часа. Каждый шаг Claude (правки, раунд конфликтов, починка) ограничен `fix.timeoutMinutes`, по умолчанию 60 минут. Установка зависимостей и каждая проверка — до 20 минут.

Цена зависит от числа замечаний и конфликтов и видна в отчёте («Цена и время») и в `fixes.jsonl`. Продолжение с сохранённой ветки дешевле: шаг правок не повторяется. Если rebase отменён до правок, на правки деньги не тратятся.

На время работы сервис запускает `caffeinate`, чтобы Mac не уснул.

## Как прервать

В окне — «Прервать» в отчёте доработки этого PR, из терминала — `bin/pr-reviewer fix stop --repo <slug> --pr <id>`. Прерывание касается только этого PR: ждущая заявка снимается из очереди, идущая доработка останавливается. Заявки других PR остаются и выполняются дальше. `fix stop` без `--repo` и `--pr` прерывает доработку, которая идёт сейчас, а очередь продолжается.

Прерывание срабатывает в любой момент, в том числе во время установки зависимостей и проверок: дочерний процесс шага останавливается сразу, а доработка — сразу после него. Доработка получает итог «доработка прервана», в `fixes.jsonl` она не пишется. Если прерывание пришло до шага пуша, ветка PR не меняется. Остатки незаконченного rebase следующий запуск уберёт сам.

## Настройки

Поля `fix` в `config.json`. Отдельных переключателей в окне нет; `config.json` можно править в окне: «Настройки» → «Дополнительно» → «config.json». Подробнее — [config.md](config.md).

| Поле | Умолчание | Что значит |
|---|---|---|
| `fix.model` | `claude-opus-5-5` | Модель Claude для доработки; модель из `agents.claude` здесь не используется |
| `fix.effort` | `high` | Уровень reasoning: `low`, `medium`, `high`, `xhigh`, `max` |
| `fix.timeoutMinutes` | `60` | Сколько ждать один шаг модели, в минутах |

Остальные параметры запуска Claude берутся из `agents.claude`.

## Известные проблемы

- Тексты в окне («Claude Opus исправит…») называют модель Opus, даже если в `fix.model` указана другая.
