# Как идёт ревью

Здесь — что именно делают модели с PR: когда они берутся за него, что видят, как публикуют замечания, как спорят друг с другом и когда закрывают свои треды. Общая схема сервиса — в [overview.md](overview.md).

## Какие PR ревьюятся фоном

Фоновое ревью берёт открытый PR, если:

- он не черновик (draft);
- его исходная ветка подходит под `branchPattern` (без поля в конфиге — `PROJ-\d+`, ветки задач; `.` — любая ветка). Остальные PR в обзоре помечены тегом «Untracked»: обычно это перенос уже проверенного кода вроде develop → master;
- у репозитория не выключено фоновое ревью;
- модель не выключена из фонового ревью (`auto: false`).

Ручной запуск — клик по иконке модели в обзоре или `review --repo … --pr … --agent …` — работает для любого открытого PR, при выключенном фоновом ревью и для модели вне фонового ревью. Он ревьюит голову заново, даже если модель уже её проверила.

## Когда модель берётся за PR

На каждом проходе сервис смотрит, есть ли модели работа:

- **новая голова PR**, которую она ещё не ревьюила;
- **треды, на которые она ещё не ответила** — корни чужих комментариев, под которыми нет её ответа;
- **свои открытые треды, которые пора перепроверить** — на новой голове или после нового ответа человека.

Если работы нет ни у одной модели и число комментариев не изменилось, PR пропускается без запуска моделей.

### Когда ревью кода пропускается

Новая голова не всегда значит новый код. Ревью головы отмечается выполненным без запуска модели, если:

- **изменения те же, что на прошлом ревью** — PR перебазировали или влили в него целевую ветку. Сравнивается отпечаток диффа (`git patch-id --stable`), он не зависит от номеров строк;
- **в PR нет изменений** относительно целевой ветки;
- **в диффе только исключённые файлы** (`ignorePaths`).

Каждый такой пропуск пишется в журнал и в `skips.jsonl`, из них считается раздел «Экономия» в статистике. Ручной запуск ревьюит всегда.

## Порядок моделей

Модели фонового ревью ходят по очереди, и каждая следующая видит комментарии всех предыдущих. Первая ревьюит код «с чистого листа» (роль `first`), следующие проверяют её замечания и добавляют свои (`second`). Когда раунд прошли все модели, первой в следующем раунде станет модель, следующая по списку за нынешней первой. На следующем проходе первая отвечает на замечания тех, кто ходил после неё.

## Что видит модель

Служебная копия переключается на голову PR, а в папку `.pr-review/` кладутся:

| Файл | Что в нём |
|---|---|
| `diff.patch` | Полный дифф PR от общего предка с целевой веткой, без исключённых файлов |
| `incremental.patch` | Изменения после прошлого ревью этой модели — если она уже ревьюила PR и новая голова продолжает старую |
| `description.md` | Описание PR, если автор его заполнил: модель проверяет, что код делает заявленное |
| `comments.md` | Все треды PR; те, где нужен её ответ, помечены «НУЖЕН ТВОЙ ОТВЕТ» |
| `backlog.md` | Уже известные проблемы репозитория из бэклога, чтобы не находить их заново (только при ревью кода) |

В промпт идут ещё правила из памяти ревьюеров (см. [memory.md](memory.md)). Модель может читать код и смотреть историю (`git diff`, `log`, `show`, `blame`), но не может править файлы: Claude получает только инструменты чтения, Codex работает в песочнице `read-only`, Cursor — в режиме `ask`.

## Замечания

### Что публикуется

Каждое замечание модель оценивает по двум осям:

- `origin` — внёс ли дефект этот PR (`pr`) или он был раньше (`preexisting`);
- `likelihood` — обычный сценарий (`usual`), редкое сочетание условий (`rare`) или только гонка или сбой (`race`).

Дальше:

- `preexisting` в PR не публикуется, а уходит в бэклог (см. [backlog.md](backlog.md));
- редкие P3 (`rare`, `race`) не публикуются: такие замечания команда отклоняет. Редкий случай модель пишет уровнем P2 и выше, только если последствие тяжёлое — потеря или порча данных, чужие данные, необратимое действие;
- остальное публикуется в PR.

Уровни: **P0** — критическая авария, **P1** — серьёзная проблема в основном сценарии, **P2** — ошибка в ограниченном сценарии, **P3** — небольшая проблема с низким влиянием. Уровень определяется последствием для пользователя, а не размером правки.

### Привязка к строке

Модель называет файл и строку. Если такой строки нет в диффе, сервис привязывает замечание к ближайшей строке диффа этого файла. Если файла нет в диффе, замечание не публикуется (в статистике — `dropped`). Замечание к удалённой строке ставится на неё, а для подсчёта исходов отслеживается по месту удаления в новой версии файла.

### Как выглядит в Bitbucket

```
[P1] Заголовок в повелительном наклонении

Сценарий: что делает пользователь и что ломается.

Причина в коде и что сделать: …

🤖 Generated with [Claude Opus 5.5](https://claude.com/claude-code)
```

По подписи (точнее, по её началу — `marker` в конфиге) сервис узнаёт комментарии своих моделей. Комментарии людей он не редактирует никогда.

## Ответы на чужие комментарии

На каждый тред с пометкой «НУЖЕН ТВОЙ ОТВЕТ» модель возвращает вердикт:

- **согласна** — утверждение верно, дефект внёс этот PR и сценарий реален. Простое согласие отдельным ответом не публикуется: в конец того комментария модели, с которым она согласна, дописывается отметка «✓ Codex проверил и согласен». Если есть что уточнить (уровень, исправление, сценарий), публикуется ответ «👍 Согласен, с уточнением: …»;
- **не согласна** — ответ «Не согласен: …» с причиной (`reason`): `wrong` — утверждение о коде неверно, `fixed` — уже исправлено на голове, `preexisting` — дефект был до PR, `unlikely` — сценарий редкий и последствие лёгкое. При `preexisting` проблема уходит в бэклог, а в ответе появляется строка «📋 Проблема была до PR — записана в бэклог для отдельной задачи.», так что тред можно закрывать;
- **пропуск** — в комментарии нет утверждения о коде (вопрос, «ок», служебное сообщение).

Модель читает тред целиком и не повторяет уточнение или возражение, которое уже высказано. Вместо этого отметка «проверил и согласен» встаёт под тем ответом другой модели, чью позицию она разделяет (`agreesWith`). Под комментариями людей и под своими комментариями отметок нет.

Если модель не ответила на какой-то тред, он всё равно считается обработанным: иначе он перезапускал бы её на каждом проходе.

## Закрытие своих тредов

На новой голове PR или после нового ответа человека модель перепроверяет свои открытые замечания и для каждого решает:

| Решение | Когда | Что происходит |
|---|---|---|
| `fixed` | Проблема устранена на голове ветки (проверяется по коду, а не по сообщениям) | В замечание дописывается «✓ Исправлено в abc1234 — Claude», тред закрывается через Resolve |
| `dismissed` | Человек ответил, что править не нужно (так задумано, не ошибка), и модель согласна по существу | Пометка «✓ Закрыто: <почему> — Claude», Resolve |
| `deferred` | Человек проблему не оспаривает, а откладывает («сделаем позже», «отдельной задачей») | Замечание уходит в бэклог, пометка «✓ Отложено в бэклог: <почему> — Claude», Resolve |
| `open` | Всё остальное: проблема на месте, спор без аргументов, ответ неясен | Тред остаётся открытым |

`dismissed` и `deferred` возможны, только если в треде ответил человек. Каждая модель закрывает только свои треды. После доработки («Исправить») треды тоже закрываются только на следующем ревью — независимо от доработки.

Проверенные треды запоминаются (`ownChecks` в `state.json`) и перепроверяются только на новой голове или после нового ответа человека. Только что опубликованные замечания считаются проверенными на своей голове. Когда PR закрывают, ближайший проход записывает исходы его замечаний и удаляет его из `state.json`, поэтому файл не растёт. Раздел отключённого репозитория остаётся намеренно: если репозиторий подключить снова, уже проверенные головы не отревьюятся заново. Сколько тредов закрыто за запуск — `closedThreads` в `stats.jsonl`; исходы — в `outcomes.jsonl` (см. [stats.md](stats.md)).

## Уровень reasoning

Ревью кода идёт с уровнем модели из конфига (`effort` у Claude, `reasoningEffort` у Codex). Запуск, где модель только отвечает в тредах, идёт с `repliesEffort` (по умолчанию `medium`): там проверяются одно-два утверждения, и высокий уровень почти ничего не даёт. Выше основного уровня он не поднимается. У Cursor уровень зашит в имя модели и не меняется. Использованный уровень пишется в `stats.jsonl` полем `effort`.

## Ревью без публикации

`bin/pr-reviewer run --dry-run --pr <id>` проходит по PR как обычно, но печатает комментарии в терминал вместо публикации и не сохраняет состояние. Модели при этом запускаются по-настоящему и тратят лимиты.
