# Память ревьюеров

Память — правила о репозитории, которые сервис выводит из комментариев команды: что задумано именно так, какие замечания команда считает ложными, какие соглашения приняты. Правила общие для всех моделей и попадают в промпт каждого ревью этого репозитория. Так модели постепенно ревьюят код так, как его ревьюит команда, и не повторяют замечания, которые уже отвергали.

## Как это работает

### Откуда берутся правила

На каждом проходе сервис ищет обсуждения с новыми комментариями людей:

- **ответы на замечания моделей** — человек ответил в треде, где уже высказалась модель; тред может быть открыт или закрыт через Resolve;
- **замечания людей в ревью** — человек сам открыл тред.

Такие обсуждения отдаются одной модели — `memory.agent` в `config.json`, по умолчанию Claude. Она выделяет устойчивые знания и формулирует их как правила для ревьюера: что проверять или чего не требовать. Подтверждения вроде «поправил», детали одного PR и общие истины программирования не берутся. Если полезного нет, модель возвращает пустой список — это частый и нормальный результат.

Для замечаний людей критерии строже. Берутся только обобщаемые правила: устройство API, обработка ошибок и транзакций, безопасность, работа с данными, архитектурные границы. Разовые предпочтения по именам, формулировкам и стилю в память не попадают.

Решение отложить проблему («сделаем позже», «отдельной задачей») правилом не становится. Такое замечание уходит в [бэклог](backlog.md), а правило «не требовать» заглушило бы его в следующих PR.

Модель видит уже известные правила и не повторяет их.

### Когда память обновляется

Память обновляется в начале прохода по репозиторию, до ревью: свежие ответы команды учитываются уже в этом проходе. Смотрятся комментарии всех открытых PR, включая черновики и PR вне `branchPattern`. Репозитории с выключенным фоновым ревью в фоне не обновляются; при ручном запуске память обновляется.

За один проход модель разбирает не больше 30 обсуждений на репозиторий, остальные ждут следующего прохода. Если вызов модели не удался, обсуждения остаются неразобранными и повторяются на следующем проходе.

Комментарии, уже разобранные памятью, запоминаются в `state.json` и второй раз модели не отдаются.

### Закрытые PR

Если PR влили или отклонили до прохода, его комментарии один раз дочитываются при закрытии. Обсуждения с новыми ответами ждут разбора в `state.json` (`closedFeedback`, не больше 100), переживают выключение фонового ревью репозитория и сбой модели.

### Как правила попадают в ревью

Все правила репозитория идут в промпт каждого запуска модели по этому репозиторию — и ревью кода, и ответов в тредах. Каждое правило — с id.

Модель отмечает, какие правила повлияли на её работу:

- `appliedLessons` — все правила, из-за которых она написала замечание, отказалась от него или изменила ответ в треде. Неизвестные id отбрасываются. Список пишется в `stats.jsonl`.
- `lessons` у замечания — правила, на которых оно основано. Пишутся в `outcomes.jsonl` вместе с исходом замечания.

По ним считаются срабатывания: сколько раз правило повлияло на ревью и сколько основанных на нём замечаний исправили и отклонили. Учёт идёт с первого ревью репозитория, в котором модели отмечали правила. Склеенное правило наследует срабатывания исходных.

### Размер памяти

Память целиком идёт в каждый промпт, поэтому её размер ограничен: `memory.maxLessons`, по умолчанию 60 правил на репозиторий.

Когда новое правило не помещается, вытесняются автоматические правила в порядке хранения — сначала самые ранние. Добавленные и исправленные вручную не вытесняются никогда. Если вручную выверены все правила, лимит превышается, а не теряется правило человека.

С 80% заполнения в обзоре висит жёлтый баннер «Память <репозиторий> почти заполнена», при полной памяти — красный «Память заполнена». Кнопка «Проверить правила» открывает лист памяти.

### Повреждённый файл

Файл памяти можно править вручную. Если после правки он стал невалидным — сломан JSON, нет массива `lessons` или у правила нет строковых `id`, `text`, `at`, — сервис его не перезаписывает:

- ревью идёт без правил этого репозитория;
- новые правила не сохраняются, а разбор обсуждений в память откладывается без запуска модели — обсуждения ждут исправления файла;
- ручные команды памяти (добавить, исправить, удалить, применить разбор) завершаются ошибкой;
- в журнал пишется ошибка.

В обзоре появляется красный баннер «Память <репозиторий> повреждена» с причиной и кнопкой «Открыть в VS Code». На значке памяти в настройках — красная точка, в листе памяти вместо правил — описание ошибки.

### Разбор памяти

Со временем в памяти копятся дубли, частные случаи и правила об удалённом коде. Разбор памяти предлагает навести порядок. Для разбора нужно хотя бы два правила.

Модель смотрит весь список вместе со срабатываниями правил и предлагает для каждого правила одно действие:

- **склеить** дубли и частные случаи одного соглашения в одно правило;
- **переписать** размытое, слишком длинное или с деталями одного PR;
- **удалить** бесполезное: деталь одного PR, общую истину, противоречие другому правилу, правило об удалённом коде;
- **оставить** как есть.

Заодно модели передаются имена из правил в \`обратных кавычках\`, которых больше нет в основной ветке: такое правило, скорее всего, устарело. Основная ветка здесь — `develop`, без неё — ветка по умолчанию служебной копии, без неё — `master`.

Правила, добавленные или исправленные вручную, разбор не трогает. Правило, о котором модель ничего не сказала, остаётся. Если план нарушает эти условия или ссылается на неизвестные правила, разбор завершается ошибкой, и план не сохраняется.

Разбор — только план, с причиной по каждому изменению. Он сохраняется и применяется отдельно, только если память не менялась после разбора. Иначе план помечается устаревшим, и нужно разобрать заново.

При применении:

- склеенное правило получает новый id и наследует срабатывания исходных;
- переписанное сохраняет id;
- перед применением память копируется в `memory/backups/`.

Последний применённый разбор можно откатить. Откат возможен, только если после разбора память не менялась, иначе выученные позже правила потерялись бы.

### Журнал изменений

Каждое изменение памяти пишется в журнал:

| Запись | Когда |
|---|---|
| «Выучено из PR» | Модель добавила правило; со ссылкой на PR |
| «Добавлено вручную», «Исправлено вручную», «Удалено вручную» | Правка человеком из окна или терминала |
| «Вытеснено» | Правило ушло при переполнении |
| «Разбор памяти» | Что удалено, склеено и переписано — «было» и «стало» с причиной |
| «Откат разбора» | Откат последнего разбора |

Ручная правка файла в редакторе в журнал не попадает.

## Как пользоваться

### В окне

Лист памяти открывается значком 🧠 с числом правил у репозитория в «Настройках» или пунктом «Память ревьюеров…» в меню репозитория. Синяя точка на значке — есть новые правила, красная — файл повреждён.

**Новые правила.** Когда модель выучила правило, в обзоре появляется синий баннер «Новые правила в памяти <репозиторий>» с последним правилом и кнопкой «Посмотреть». Баннер закрывается крестиком; подсветка в настройках остаётся, пока лист памяти не откроют. В листе новые правила отмечены синими точками и считаются просмотренными после закрытия листа. Правила, добавленные вручную, новыми не считаются. Что просмотрено, хранится в настройках приложения, а не у сервиса.

Лист памяти состоит из трёх вкладок.

**«Правила».** Правила от новых к старым. У каждого:

- откуда оно: «из ревью PR #N» или «из ответа в PR #N» со ссылкой и авторами, «добавлено вручную», «исправлено вручную», «склеено разбором»;
- когда добавлено;
- срабатывания: «сработало: N», замечаний на его основе — сколько исправлено и отклонено, или «не срабатывало».

Над списком — с какой даты идёт учёт и сколько ревью в него попало. Карандаш исправляет правило (это `memory edit`), корзина удаляет без подтверждения. Поле внизу добавляет своё правило.

**«Разбор».** Кнопка «Разобрать память» запускает разбор; лист можно закрыть, разбор продолжится, а план появится на этой вкладке. Число на вкладке — сколько изменений предложено. План показан как итог и группы «Склеить», «Переписать», «Удалить» — с причиной, текстом «было» и «станет». В «было» красным подсвечены слова, которых не останется, в «станет» зелёным — новые.

- «Применить» применяет план и перечитывает память;
- «Отказаться» удаляет план, память остаётся как есть;
- если память изменилась после разбора, план помечен устаревшим, и вместо «Применить» — «Разобрать заново».

Сохранённый план открывается сразу на этой вкладке. Окно берёт его из `memory review <slug> --show --json`: у плана есть поле `outdated`, а если плана нет, печатается `null`.

**«Что менялось».** Журнал изменений: последние 100 записей, от новых к старым, с типом, точной датой и ссылкой на PR у выученных правил. Добавленные отмечены плюсом, удалённые и вытесненные зачёркнуты, рядом причина. У переписанных и склеенных — «было» и «стало» с той же подсветкой, что в плане. У последнего применённого разбора есть кнопка «Откатить»: она спрашивает подтверждение и вызывает `memory restore`. Если сервис отказывает, его сообщение показывается над журналом.

**Пустая память.** Вместо вкладок — «Изучить историю репозитория»: модель читает комментарии людей в последних 50, 100 или 300 PR — открытых, влитых и отклонённых — и выделяет правила. Это `memory learn`. Займёт несколько минут; итог — строка «Правил в памяти: было …, стало …».

**Массовая правка.** Кнопка со стрелкой в заголовке листа открывает файл памяти в VS Code. Сохранённые изменения окно подхватит само.

Подробнее про окно — [window.md](window.md).

### В терминале

```
bin/pr-reviewer memory list <slug> [--json]
bin/pr-reviewer memory add <slug> <текст>
bin/pr-reviewer memory edit <slug> <id> <текст>
bin/pr-reviewer memory remove <slug> <id>
bin/pr-reviewer memory learn <slug> [--prs <N>] [--dry-run]
bin/pr-reviewer memory review <slug> [--show] [--json] [--discard]
bin/pr-reviewer memory apply <slug>
bin/pr-reviewer memory history <slug> [--limit <N>] [--json]
bin/pr-reviewer memory restore <slug>
```

- `list` — правила с происхождением и срабатываниями. С `--json` — `{ since, runs, lessons }`, у каждого правила поле `usage` (`applied`, `findings`, `addressed`, `dismissed`) или `null`.
- `learn` — разово разобрать комментарии людей из последних N PR любого состояния (по умолчанию 100). `--dry-run` только считает обсуждения, модель не запускается. Уже разобранные комментарии пропускаются.
- `review` — разобрать память и показать план. `--show` — показать сохранённый план без нового разбора, `--json` — в JSON, `--discard` — удалить план.
- `apply` — применить сохранённый план.
- `history` — последние 30 записей журнала, `--limit <N>` — другое число, `--json` — весь журнал.
- `restore` — откатить последний применённый разбор.

`learn` (без `--dry-run`), `apply` и `restore` не запускаются, пока идёт проход ревью: память в это время может меняться. Полный справочник — [cli.md](cli.md).

## Где хранится

| Файл | Что в нём |
|---|---|
| `~/Library/Application Support/pr-reviewer/memory/<slug>.json` | Правила репозитория |
| `~/Library/Application Support/pr-reviewer/memory/<slug>.history.jsonl` | Журнал изменений |
| `~/Library/Application Support/pr-reviewer/memory/<slug>.review.json` | Сохранённый план разбора |
| `~/Library/Application Support/pr-reviewer/memory/backups/` | Копии памяти перед применением разбора — для отката |
| `~/Library/Application Support/pr-reviewer/state.json` | Какие комментарии уже разобраны (`learned`) и обсуждения закрытых PR, ждущие разбора (`closedFeedback`) |

Поля правила в `memory/<slug>.json`:

| Поле | Что это |
|---|---|
| `id` | Id правила; обязательно |
| `text` | Текст правила; обязательно |
| `at` | Когда добавлено; обязательно |
| `source` | Откуда выучено: `pr`, `url`, `commentIds`, `authors`, `kind` (`reply` — ответ модели, `review` — замечание человека). У склеенного — ещё `mergedFrom`: id исходных правил и тех, из которых были склеены они сами |
| `mergedFrom` | То же, если у склеенных правил не было источника (например, все добавлены вручную) |
| `manual` | Добавлено вручную |
| `edited` | Исправлено вручную |
| `rewrittenAt` | Когда переписано разбором |

Остальные файлы сервиса — в [data.md](data.md).

## Сколько стоит

Память ведёт модель `memory.agent`, каждый её вызов — отдельный запуск. Цена пишется в `spend.jsonl`: `memory-learn` — разбор обсуждений, `memory-review` — разбор памяти. На вкладке «Статистика» она видна в «Стоимости» как «Память». Как считается цена — в [stats.md](stats.md).

По журналу сервиса:

- разбор обсуждений — $0.05–0.13 за вызов, в среднем около $0.09 и 10 секунд;
- разбор памяти — около $0.1–0.2 и 1–3 минуты.

Правила в промпте ревью увеличивают каждый запуск ревью на объём памяти — это ещё одна причина держать её небольшой.
