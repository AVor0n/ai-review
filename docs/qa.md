# Тестирование в браузере

Тестирование проверяет PR тестами и в живом приложении: исправлен ли баг или работает ли фича, и не сломалось ли что-то рядом. Claude составляет план с кейсами, вы его смотрите и правите, потом Claude пишет и запускает тесты — юнит и компонентные на Vitest, e2e на Playwright против локального бэкенда в Docker. Тесты можно сохранить в свою копию репозитория.

Пока только для фронтенда (`qa.frontend`, по умолчанию `frontend`), только вручную и в два этапа: план, затем прогон. Отчёт только локальный, в PR ничего не публикуется.

## Как запустить

**Из окна.** В строке PR на вкладке «Обзор», правее колонны архитектурного ревью, — пробирка. Она есть только у PR репозитория из `qa.frontend`. Клик открывает лист тестирования с вкладками «План» и «Отчёт». Подробнее об окне — [window.md](window.md).

- «План»: поле «На что обратить внимание» и кнопка «Составить план».
- Готовый план: снимите галочки с лишних кейсов, допишите «Свои кейсы» (каждая строка — отдельный кейс) и нажмите «Запустить прогон…». Окно спросит подтверждение и предупредит, сколько это займёт.
- «Отчёт» появляется после прогона. Из него можно сохранить тесты в репозиторий.

**Из терминала:**

```
bin/pr-reviewer qa plan --repo frontend --pr <id> [--note "на что смотреть"]
bin/pr-reviewer qa run  --repo frontend --pr <id> [--only C1,C3] [--skip C2] [--add "что проверить"]… [--note "…"]
bin/pr-reviewer qa show --repo frontend --pr <id> [--plan] [--json]
bin/pr-reviewer qa save --repo frontend --pr <id>
bin/pr-reviewer qa list [--json]
bin/pr-reviewer qa stop --repo frontend --pr <id>
```

`qa plan` и `qa run` только ставят заявку в очередь; работа идёт отдельным фоновым процессом. Для других репозиториев они отвечают ошибкой. Тестирование запускается и на паузе фонового ревью. Все команды — в [cli.md](cli.md).

## Что происходит

Планы и прогоны идут по одному, в порядке очереди. Обычное ревью в это время не стоит. Работа идёт в служебной копии `~/.pr-reviewer/qa-workspaces/<slug>`, переключённой на голову PR; ваша локальная копия меняется только по `qa save`.

### Этап 1. План

1. PR должен быть открыт. Если в клоне нет коммита PR или целевой ветки, сервис скачивает `origin`; если коммита нет и после этого — ошибка «подождите минуту и запустите снова».
2. Claude получает:
   - дифф PR без файлов из исключений (`ignorePaths`); пустой дифф — ошибка;
   - коммиты ветки;
   - описание PR, если автор его заполнил;
   - комментарии ревью;
   - отчёт архитектурного ревью, если оно было;
   - правила из памяти ревьюеров этого репозитория;
   - ваши пожелания из `--note`.

   Сам он читает стратегию тестирования репозитория (`docs/testing-strategy.md`), код и тесты, в том числе e2e-фикстуры с тестовыми данными.
3. Claude определяет, что за PR (исправление ошибки, новая функциональность, переделка без изменения поведения, другое), как должно работать после него, выписывает опасные места и составляет кейсы. Порядок кейсов: сначала ваши из `--note`, потом проверка самого изменения, потом регрессии рядом. Кейсы нумеруются C1, C2, …
4. Если проверять нечего (например, PR меняет только инструменты разработки), план так и говорит; прогон можно запустить на своих кейсах.

У каждого кейса — уровень по стратегии тестирования. Берётся самый дешёвый уровень, который честно проверяет поведение; на внутренности легаси тесты не планируются.

| Уровень | Что проверяет | Чем |
|---|---|---|
| Юнит | Чистые функции, селекторы, адаптеры DTO | Vitest, тест рядом с кодом |
| Компонентный | Страница, панель, виджет со своим состоянием | Vitest и Testing Library, тест рядом с компонентом |
| e2e | Экран и путь пользователя против бэкенда | Playwright |

Ещё у кейса — источник (ваш, изменение, регрессия), важность (`high` — без этого PR нельзя вливать, `medium`, `low`), данные, шаги и ожидаемый результат. У юнит и компонентных — проверяемый файл. Отдельный раздел «Не проверить» — что важно, но тестом на тестовой базе не проверить, и почему. В планах, составленных до появления уровней, все кейсы считаются e2e.

### Этап 2. Прогон

Прогон без плана невозможен. Набор кейсов:

- `--only C1,C3` — только эти кейсы плана, `--skip C2` — все, кроме этих. id можно писать в любом регистре; id, которого нет в плане, — ошибка.
- `--add "что проверить"` — свой кейс, можно несколько раз. Такие кейсы получают id U1, U2, …, важность `high` и идут первыми. Шаги, ожидаемое и уровень Claude выбирает сам.
- Пожелания из `--note` передаются в прогон. В окне снятые галочки становятся `--skip`, строки «Своих кейсов» — `--add`, поле «На что обратить внимание» — `--note`.

Дальше:

1. **Рабочая копия и зависимости.** Зависимости ставятся, только если сменился lock-файл.
2. **Окружение для e2e.** Нужно, если среди кейсов есть e2e или свои кейсы (свой кейс может оказаться e2e). Без них Docker и браузер не нужны, этот шаг пропускается.
   - Ставится браузер: `yarn playwright install chromium`.
   - Проверяется, что Docker доступен; иначе — ошибка «Docker недоступен».
   - Собирается образ бэкенда `pr-reviewer-qa-backend:<коммит>` по `docker/backend.e2e.Dockerfile` из репозитория фронтенда. Образ собирается один раз на коммит бэкенда; первая сборка — несколько минут. Бэкенд (`qa.backend`) должен быть подключён в `repos`.
   - Поднимается e2e-окружение из `docker-compose.e2e.yml` со свежей тестовой базой из дампа.
   - Запускается фронтенд из ветки PR: `yarn start` на свободном порту, с моками, как в e2e.
3. **Тесты.** Claude читает стратегию тестирования и пишет тесты по её правилам:
   - юнит и компонентные — новыми файлами `*.test.ts(x)` рядом с кодом в `src/`;
   - e2e — по Playwright-тесту на кейс, на `authenticatedTest` и фикстурах из `e2e/utils`.

   Заголовок каждого теста начинается с `[<id>]`, например `[C2] Сохранение черновика`: по нему итоговый прогон находит кейс. Claude запускает тесты, отличает ошибку в тесте от ошибки приложения и чинит тесты. Если до проверяемого состояния не добраться за три попытки, кейс помечается «не удалось проверить». Для каждого теста Claude называет место в репозитории по стратегии: юнит и компонентные остаются, где написаны, e2e — `e2e/<домен>.test.ts`.
4. **Итоговый прогон.** Сервис сам прогоняет все тесты ещё раз: Vitest с JSON-отчётом (все новые и изменённые тесты в `src/`) и Playwright, у которого берёт видео и скриншоты. Статус кейса определяется по этому прогону, а не по словам модели (см. ниже).
5. **Остановка.** Фронтенд и e2e-окружение останавливаются, контейнеры и том базы удаляются — и после удачного прогона, и после ошибки.

### Ветка бэкенда

Сервис ищет ветку бэкенда той же задачи, чтобы фича, которую делали в двух репозиториях, проверялась целиком:

- номер задачи берётся из `PROJ-<n>` в имени ветки фронтенда или из ветки, названной одним числом;
- подходит ветка бэкенда, где это число стоит отдельно (не частью другого числа);
- если такой ветки нет или их несколько — берётся `develop`.

Какая ветка и коммит бэкенда использованы, видно в отчёте.

### Окружение

Окружение тестирования отдельное от вашего e2e: свой проект compose `pr-reviewer-qa`, свои имена контейнеров, бэкенд на порту 48180, база наружу не публикуется. Поэтому прогон можно запускать, пока у вас открыт `yarn e2e:ui` или стенд local. Но это ещё один бэкенд и сборка образа, то есть заметная нагрузка на Mac.

Адрес бэкенда задан в сгенерированном конфиге Playwright: иначе `authenticatedTest` пошёл бы в ваш e2e-бэкенд на 48080. Настройки Playwright: один воркер, без повторов, окно 1600×900, язык `ru-RU`, часовой пояс `Europe/Moscow`, видео и скриншоты каждого теста, trace при падении.

Собранные образы бэкенда сервис не удаляет: они копятся в Docker по одному на коммит бэкенда.

### Статусы кейсов

| Статус | Когда |
|---|---|
| Прошёл | Итоговый прогон прошёл, и модель не сообщала об ошибке |
| Ошибка приложения | Итоговый прогон упал, и модель тоже нашла ошибку приложения |
| Не подтверждено | Модель и итоговый прогон расходятся, или теста для кейса в итоговом прогоне нет |
| Не удалось проверить | Модель не смогла добраться до проверяемого состояния |
| Пропущен | Модель сочла кейс дублем другого |

Файл Vitest, который не собрался, считается упавшим тестом тех кейсов, которые модель в нём назвала. У несобравшегося файла Playwright в отчёте нет тестов, и его кейсы получают «Не подтверждено».

## Что разрешено модели

На этапе плана модель только читает: файлы, `git log`, `git show`, `git diff`. Ничего не запускает и не меняет.

На этапе прогона:

- писать и править `*.test.ts` и `*.test.tsx` в `src/` и файлы в `.pr-review/qa/cases/` (там лежат e2e-тесты);
- запускать тесты: `yarn vitest --run --project=unit …` и `yarn playwright test` со сгенерированным конфигом;
- читать файлы и git: `git diff`, `git log`, `git show`, `git status`.

Код приложения, коммиты и Docker ей недоступны. Запрет менять уже существующие тесты есть только в промпте: технически правка `*.test.ts(x)` в `src/` разрешена любая.

## Где результат

**В окне.** Пробирка в строке PR:

| Пробирка | Что значит |
|---|---|
| Серая | Тестирования не было |
| Синяя | План готов |
| Часы | План или прогон в очереди |
| Крутится | Идёт план или прогон |
| Красная | Прогон нашёл ошибку приложения |
| Оранжевая | Есть неподтверждённые или непроверенные кейсы |
| Зелёная | Всё прошло |
| Треугольник | План или прогон не удался |

Лист тестирования:

- **План.** Суть и тип PR, как должно работать, опасные места с путями, кейсы с галочками и метками уровня, источника и важности (по клику раскрываются проверяемый файл, данные, шаги и ожидаемое), «Свои кейсы», «Не проверить», коммит и цена плана. Если голова PR ушла от коммита плана — плашка «План устарел».
- **Отчёт.** Итог и счётчики по статусам, окружение, по каждому кейсу — статус, уровень, файл теста, что проверено, найденная ошибка, заметки, расхождение модели и итогового прогона, ошибки Playwright и галерея скриншотов и видео. Клик по превью открывает файл в большом окне просмотра. Плашки — если план и прогон на разных коммитах или PR ушёл вперёд.
- **Тесты** (в отчёте) — файлы прогона с местом в репозитории и кнопка «Сохранить в frontend» (`qa save`).
- Пока идёт работа — строка статуса с таймером и текущим действием, во время прогона — ход по шагам и «Прервать». Ошибка сервиса показывается целиком, отказ команды (нет плана, не тот репозиторий) — плашкой в листе.
- «Скопировать план» и «Скопировать отчёт» кладут в буфер вывод `qa show` (с `--plan` или без), «Открыть папку прогона» открывает папку прогона в Finder.

Уведомлений о готовом плане или прогоне нет.

**В терминале.** `qa show` после прогона показывает отчёт, а до прогона или с `--plan` — план. Если последний прогон не удался, сверху строка «Последний прогон не удался: <ошибка>». `qa list` — все PR с тестированием и их состояние.

**Файлы.**

- `~/Library/Application Support/pr-reviewer/qa/state/<repo>__<pr>.json` — план, последний прогон и куда сохранены тесты.
- `~/Library/Application Support/pr-reviewer/qa/runs/<repo>__<pr>/<время>/` — файлы прогона: видео и скриншоты в папках кейсов (`C1/`, `U1/`…), тесты — в `tests/` с путями как в рабочей копии.
- `~/Library/Application Support/pr-reviewer/qa.jsonl` — история. Планы пишутся с `stage: plan` (голова, тип PR, число кейсов, цена), прогоны — с `stage: run` (голова, число кейсов по статусам, число найденных ошибок, цена, длительность). Неудачные и прерванные планы и прогоны сюда не пишутся.

Все файлы — в [data.md](data.md).

### Сохранить тесты

`bin/pr-reviewer qa save --repo frontend --pr <id>` или «Сохранить в frontend» в отчёте. Тесты последнего прогона копируются в вашу локальную копию репозитория (`source` у репозитория в `config.json`) по местам из стратегии, **без коммита**: вы смотрите их и коммитите сами.

- Нужна локальная копия с `.git` по пути `source`; иначе — ошибка.
- Во время прогона сохранять нельзя.
- Относительные импорты пересчитываются: e2e-тест переезжает из `.pr-review/qa/cases/` в `e2e/`, и `../../../e2e/utils/test` становится `./utils/test`.
- Существующий файл не перезаписывается: тест ложится рядом с суффиксом `.pr<id>` (`analysisDrafts.pr2795.test.ts`), потом `.pr<id>-2` … `.pr<id>-9`; если заняты и они — ошибка. Повторное сохранение того же текста новых копий не создаёт.
- Если копия на другой ветке, чем PR, команда и окно предупреждают: тесты написаны под код PR и до переключения на его ветку могут не пройти.
- e2e-тесты написаны на `authenticatedTest`. Для сценариев, меняющих данные, стратегия требует фикстуру `test` со сбросом БД — её нужно поставить вручную; модель отмечает такие кейсы в заметках.

## Сколько длится и сколько стоит

| Что | Сколько |
|---|---|
| План | Несколько минут, около доллара |
| Прогон с e2e | 30–60 минут и несколько долларов, заметная нагрузка на Mac |
| Прогон без e2e | Заметно быстрее и дешевле: только Vitest, без Docker и браузера |

Пределы времени:

| Шаг | Предел |
|---|---|
| Этап модели (план или тесты) | `qa.timeoutMinutes`, по умолчанию 90 минут |
| Установка браузера | 15 минут |
| Сборка образа бэкенда | 40 минут |
| Подъём e2e-окружения | 20 минут |
| Старт фронтенда | 5 минут |
| Один тест Playwright | 3 минуты |
| Итоговый прогон Playwright | 40 минут |
| Итоговый прогон Vitest | 20 минут |

Точная цена — в листе тестирования и в `qa.jsonl`. На время работы сервис запускает `caffeinate`, чтобы Mac не уснул.

## Как прервать

В окне — «Прервать» в листе тестирования (видна, пока план или прогон ждёт в очереди или идёт), из терминала — `bin/pr-reviewer qa stop --repo <slug> --pr <id>`. Прерывание касается только этого PR: ждущая заявка снимается из очереди, идущий план или прогон останавливается. Заявки других PR остаются и выполняются дальше. `qa stop` без `--repo` и `--pr` прерывает то, что идёт сейчас, а очередь продолжается.

Прерывание срабатывает в любой момент, в том числе во время сборки образа, подъёма окружения и итогового прогона: дочерний процесс шага останавливается сразу, а тестирование — сразу после него. Затем сервис останавливает фронтенд и e2e-окружение. Прерванный план получает итог «план прерван», прерванный прогон — «тестирование прервано».

## Настройки

Поля `qa` в `config.json`. Отдельных переключателей в окне нет; `config.json` можно править в окне: «Настройки» → «Дополнительно» → «config.json». Подробнее — [config.md](config.md).

| Поле | Умолчание | Что значит |
|---|---|---|
| `qa.frontend` | `frontend` | Репозиторий фронтенда, PR которого можно тестировать |
| `qa.backend` | `backend` | Репозиторий бэкенда для образа Docker; должен быть подключён в `repos` |
| `qa.model` | модель из `agents.claude` | Модель Claude для плана и прогона |
| `qa.planEffort` | `high` | Уровень reasoning для плана: `low`, `medium`, `high`, `xhigh`, `max` |
| `qa.effort` | `high` | Уровень reasoning для прогона |
| `qa.timeoutMinutes` | `90` | Сколько ждать один этап модели, в минутах |

Модель всегда Claude; остальные параметры запуска берутся из `agents.claude`.

## Известные проблемы

- Правила памяти ревьюеров получает только план; в промпт прогона они не передаются.
